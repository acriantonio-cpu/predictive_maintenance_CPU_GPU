# Standards and interoperability (requirement 15.6)

> English copy of [`docs/interoperabilita.md`](../interoperabilita.md) (Italian); keep them in sync.

## Open schema

`schemas/*.schema.json` (JSON Schema 2020-12, version `1.0`) describes aggregated samples,
indicators, maintenance events, chart state and signals. `hwdrift export --format jsonl` produces
conforming records; `scripts/validate_export.py` validates them and runs in CI.

Principles: UTC timestamps in integer milliseconds; channel names `component.measure_unit` in
lowercase (`cpu.pkg.temp_c`, `gpu0.power_w`); no hardware identifiers; `machine_id` random and
local; `maintenance.*` events as labels for validation.

## Prometheus / OpenMetrics

`hwdrift export --format prometheus --out C:\node_exporter\textfile\hwdrift.prom` produces the
text exposition format for the *textfile collector* of node_exporter / windows_exporter:

- `hwdrift_indicator{indicator,regime,level}`: latest value of every indicator;
- `hwdrift_chart_limit{indicator,regime,level,limit=center|ucl|lcl}`;
- `hwdrift_active_alerts{level}`;
- `hwdrift_last_sample_timestamp_seconds`.

No HTTP server: the file is regenerated by a scheduled task after `analyze`.

## OpenTelemetry

`hwdrift export --format otlp` writes an OTLP/JSON file (`resourceMetrics` → `scopeMetrics` →
gauge `hwdrift.indicator` with attributes `indicator`, `regime`, `level`; resource
`service.name=hwdrift`, `host.id=<machine_id>`). No network sending: the file can be read by an
OpenTelemetry Collector with the `otlpjsonfile` receiver.

## Existing conventions to check before extending the schema

- OpenTelemetry *hardware* semantic conventions (`hw.temperature`, `hw.fan.speed`, `hw.power`,
  `hw.status`, attributes `hw.id`, `hw.type`): a 1:1 mapping of the canonical channels in a future
  version of the export is possible.
- node_exporter `node_hwmon_temp_celsius`, `node_hwmon_fan_rpm`: useful names for those who
  already use Prometheus on Linux.
- Log formats of HWiNFO and LibreHardwareMonitor: supported on import.
